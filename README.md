# 托育开放日探访协调后端

准备入托的家长希望在开放日看清教室与照护方式，却不愿自己的孩子将来被陌生访客拍进社交平台；园方若完全禁止观察，又失去建立信任的机会。本项目是协调这一张力的后端：园方先行发布可看的范围，访客凭限时凭证按容量到访，在园儿童的监护人分项决定观察、摄影与宣传，突发情况可局部暂停并改期，撤回授权只影响未来而不抹掉历史。

资料只包含领域约定与可运行的领域逻辑，不含真实个人信息、生产连接或外部账号。

## 设计要点

- **事件溯源、仅追加**：所有事实都是不可变事件（`src/store.js`）。撤回同意、作废凭证、撤下材料都表现为*新事件*，历史记录从不消失。
- **状态从事件流重放**：`buildState`（`src/state.js`）机械重放事件；业务规则集中在 `OpenDayService`（`src/service.js`），纯判定集中在 `src/policies.js`。
- **同意按时间点生效**：观察 / 摄影 / 宣传三项彼此独立，分别由监护人决定；未表态默认拒绝。撤回只改变撤回时刻*之后*的活动，撤回前的合法进入与拍摄事实保留；已发布材料进入可跟踪的**处置流程**（定位 → 限制 → 撤下 → 清副本 → 归档），而不是从记录中删除。
- **现场容量**：预约名额与现场清点分开。入园与再次进入都校验容量；临时离场释放现场名额（消防清点准确），但保留其再入名额。
- **局部暂停与全园封控**：突发照护、传染病风险可暂停指定区域；消防要求触发全园封控，停止一切入园、再入与区域进入。暂停影响到的家庭自动获得改期邀约，接受后旧凭证作废、换发新时段凭证。
- **员工最小授权**：接待只接触接待所需字段（白名单）；安全值班只看到处置突发所需的在场与动线信息；负责人拥有全量协调与闭园报告。授权在每个命令处校验。
- **闭园可交代**：负责人报告说清每位访客到过哪些区域及时间、哪些影像允许保留 / 处置到第几步、投诉与删除请求走到哪个阶段、访问期间是否发生过撤回。

## 目录

- `src/childcare_open_day.js`：事件种类、角色、同意范围、暂停原因、处置步骤等领域常量与事件校验。
- `src/store.js`：仅追加、深度冻结的事件存储。
- `src/state.js`：事件 → 状态的归约器（含同意决定史、动线、暂停史、影像、案件）。
- `src/policies.js`：时点同意、区域政策、凭证可用性、容量、暂停影响面等纯函数。
- `src/service.js`：`OpenDayService` 命令模型（发布、登记、凭证、同意/撤回、出入、暂停/改期、影像处置、案件、闭园）。
- `src/views.js`：公开目录、接待/安全/负责人视图与闭园报告。
- `src/errors.js`：带稳定错误码的领域错误。
- `tests/`：契约与业务规则测试（46 个）。

## 一次开放日的流程

1. 负责人 `publishOpenDay`：发布开放区域、时段、人数、讲解语言、无障碍条件。
2. 接待 `registerVisitor`：登记同行人与关注事项，系统按容量自动签发**限时凭证**。
3. 负责人代监护人 `recordConsent`：分别记录观察、摄影、宣传是否获准。
4. 接待 `checkIn` / `temporarilyExit` / `reenter` / `checkOut`，并 `enterArea` / `exitArea`；进入区域时按当时该区域儿童的同意实时裁定，拒绝会留痕。
5. 安全值班 `pauseRoute`（突发照护 / 传染病 / 消防）→ 受影响家庭 `offerReschedule` / `respondReschedule`，事后 `resumeRoute`。
6. 影像 `logMedia`：登记时即按当时授权判定保留或进入处置；撤回后 `flagMediaForDisposal` 并逐步 `recordDisposalStep`。
7. 投诉或删除请求 `openCase` / `advanceCase` / `closeCase`。
8. 负责人 `closeOpenDay`（仍有访客在园需显式确认）后，用 `ownerClosingReport` 输出交代报告。
